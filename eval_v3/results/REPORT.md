# Shopping Agent 工程评测（2026-09-29）

## 1. 数据、口径与隔离

- A：从 ShoppingBench 官方 product 250 条及本地已匹配商品记录生成 `eval_v3/datasets/product_250_local.jsonl`。250 个目标 `product_id` 与本地语料逐条一致。输入是完整本地标题、确定性截短标题、商品实际属性组成的短需求；**没有使用官方自然语言 query，也没有调用模型 API**。属性缺失的 15 条回退为截短标题。整个语料约 274 万件商品。
- B：6 条自然复杂任务，另有 9 条首步委派探针。调用真实模型与工具；每次运行新建隔离 SQLite。写入均是本地模拟购物动作。
- C：自建 5 条、每条 6–7 轮的逐轮会话（预算/品牌/颜色改动及鼠标＋键盘双商品），分别跑默认压缩与保留完整历史。每轮真实调用 `ShoppingService.recommend_for_session` 和配置的模型 API。对最终商品卡按标注条件计算：**ASR** 为全部条件满足的案例比例，**CAR** 为条件满足比例的平均值；另给出任一候选卡满足全部条件的比例。该口径是工程自建评分，**不是** ShoppingBench 官方学习型标题相似度评分。
- D：6 组隔离的跨会话冲突，覆盖颜色、品牌、预算、尺码和不同记忆类型。新记忆应覆盖同主题同槽位旧记忆，不相关偏好应留下。

## 2. A：250 条纯检索

下表的相关性是严格匹配唯一目标商品 ID；`R@K` 即 Recall@K。完整标题和属性档的精排全量运行成本过高，主四路对比使用截图指定的**截短标题档 250/250**。

| 输入档位 | 方法 | R@1 | R@5 | R@8 | MRR@8 | NDCG@8 |
|---|---|---:|---:|---:|---:|---:|
| 完整标题，250 | BM25 | 65.6% | 86.8% | 90.8% | .748 | .787 |
| 完整标题，250 | 向量 | 71.6% | 90.0% | 91.6% | .791 | .822 |
| 完整标题，250 | 融合 | 71.2% | 91.2% | **94.4%** | .791 | .828 |
| 截短标题，250 | BM25 | 42.0% | 61.2% | 69.6% | .506 | .551 |
| 截短标题，250 | 向量 | 24.0% | 41.6% | 48.0% | .313 | .353 |
| 截短标题，250 | 融合 | 41.2% | 66.0% | 73.2% | .511 | .564 |
| 截短标题，250 | 融合＋精排 | **53.2%** | **73.2%** | **76.8%** | **.606** | **.645** |
| 属性短需求，250 | BM25 | 44.8% | 60.0% | **64.8%** | **.510** | **.544** |
| 属性短需求，250 | 向量 | 16.4% | 27.6% | 31.2% | .206 | .231 |
| 属性短需求，250 | 融合 | 28.0% | 55.2% | 62.0% | .389 | .445 |

目标进入两路候选池的比例：完整标题 **99.6%**、截短标题 **93.6%**、属性短需求 **84.4%**。完整标题另有前 70 条成对精排探针：该子集融合 R@8 90.0%，融合＋精排 91.4%；它不能冒充 250 条全量结果。

**判断。** 官方 250 条本身并非低召回的主因。完整标题可达 94.4%，截短信息仍有 76.8%；以前直接用官方长自然语言 query、跳过 Agent 的约束改写，与纯检索的口径不同。属性档变弱是因为短需求词少、属性字段不完整，向量路尤其弱；固定权重融合在这一档还低于 BM25（62.0% 对 64.8%）。精排在截短档有效，但 CPU 精排 P95 约 **24.8 秒**，是前端交互的明显延迟瓶颈。各档计时受并发评测负载影响，只宜作量级参考。

## 3. B：多 Agent 与购物动作

旧自然复杂集委派率为 0。提示词明确独立任务应同轮双委派后，9/9 首步探针都出现双委派。最终版源码上 6 条完整自然复杂任务的结果：

| 指标 | 结果 |
|---|---:|
| 完成并成功 | 6/6 |
| 有真实子 Agent 委派 | 5/6 = 83.3% |
| 独立子任务并行批次 | 5 |
| 平均并行加速（子任务耗时和／并行墙钟） | 1.67 倍 |
| 主 Agent 工具调用数均值 | 3.17 |
| 3 条加购任务的已写入商品均出现在卡片 | 3/3 |
| 非用户要求的购买 | 0 |
| 任务耗时 P50 / P95 | 47.7 秒 / 64.7 秒 |

BX04 这次由主 Agent 自己完成“读状态＋搜索”，所以任务成功但**不计入委派**。相同六条在前一次运行的委派率为 6/6，显示模型编排有波动。旧评测器先漏看子 Agent 的 `read_state`，随后又只认子 Agent 的读取而把主 Agent 直接完成误判失败；还复用了包含旧购物车的 SQLite，导致“写入未展示”的误判。新评测器同时核对主/子真实调用并从空库开始。B 的 6/6 任务成功是小样本工程探针，不能外推为全场景成功率。

## 4. C：真实逐轮上下文

最终同一版源码下，两组相同的 5 条均已完整完成；压缩组 5/5 触发了摘要，最终保存的文本 token 平均为未压缩历史的 **85.3%**。所有案例均未意外下单。按最终首张商品卡评分：

| 模式 | 完成率 | ASR | CAR | 任一候选卡 ASR | 历史保留比例 |
|---|---:|---:|---:|---:|---:|
| 压缩历史 | 5/5 | **5/5 = 100%** | **100%** | **5/5 = 100%** | 85.3% |
| 完整历史 | 5/5 | **5/5 = 100%** | **100%** | **5/5 = 100%** | 100% |

两组各 34 轮均成功，记忆抽取错误均为 0；压缩组单轮耗时 P50/P95 为 31.3/71.1 秒，完整历史组为 25.6/83.8 秒。两组同时运行，CPU 与 API 负载互相影响，耗时不能作为压缩是否加速的因果证据。

修复前的同样 5 条，压缩组首卡 ASR 为 **3/5**、CAR **86.7%**，完整历史组为 **4/5**、CAR **93.3%**。白色背包原来只把 `color=white` 拼进检索词，没有验证最终候选的颜色；压缩组因此把无白色证据的商品放到首卡。增加商品字段颜色过滤后，单条七轮定点复测 ASR/CAR 均为 1，最终完整五条复测也通过。商品可以有多种颜色选项，当前数据没有 SKU 级库存，颜色评分仅验证本地标题/描述是否列出该颜色。

鼠标＋机械键盘双商品案例在修复前两组回答都列出两类商品，最终八张卡却只出现鼠标，故严格双目标 ASR 失败。定位到自然 `category="mechanical keyboard"` 在旧检索工具中筛出 **0 件**（相同查询不传类目或传 `keyboard` 都返回 **8 件**）；修复类目短语解析和多路卡片交错展示后，单条六轮定点复测双目标 ASR/CAR 均为 1。评分器也排除了“mechanical touch”且 `keyboard_switch_type=membrane` 的膜式键盘，最终选中的键盘有真实轴体属性。最终完整五条复测通过。

早期逐轮探针还揭示三个真实故障：记忆抽取无效 JSON 会让完成的购物轮次丢失；摘要 API 的输出 token 被推理耗尽后返回空正文；新摘要加入后仍超预算时没有继续压缩较早消息。三者已修复，并通过原隔离会话续跑验证。**5/5 是小规模可行性结果**，多任务与长对话仍需要更大、独立于本次修复过程的留出集复测。

## 5. D：近期记忆优先

6/6 冲突用例通过：同主题的黑→白、罗技→雷蛇、旧→新预算/尺码，旧记录被标为 `SUPERSEDED`，跨会话注入只读到新记录；6/6 不相关偏好保持，6/6 新记忆位于读取首位。规则识别仍限于明确的商品主题及颜色、品牌、预算、尺码、连接方式，模糊自由文本冲突可能尚未合并。旧 20 条记忆抽取基线的严格 precision/recall 均为 77.8%，属于另一个“抽取质量”指标，不能用 6/6 冲突结果替代。

## 6. 复现、修改与剩余限制

- 生成：`python eval_v3/prepare_product_queries.py`；四路检索：`python eval_v3/retrieval_four_way.py --tier partial --limit 250`。完整标题和属性档省略精排时加 `--skip-rerank`。逐条 ID、排名、耗时及汇总在本目录 JSON。
- B：`python eval_v3/multiagent_full.py --group natural_complex`。C：`python eval_v3/context_end_to_end.py --label <名称> --context-mode compressed|full`，评分口径更新后运行 `rescore_context.py`。D：`python eval_v3/memory_conflict_eval.py`。
- 业务源码和评测口径的逐项变更见 [`../CHANGES.md`](../CHANGES.md)。
- 旧 `eval_v2` 执行脚本已删除，仅保留历史数据和结果；本轮所需官方原始 250 条、B 案例、指标和评分器均在 `eval_v3/` 内，可独立运行。
- 进一步提升应先处理属性档的向量召回和融合权重，再减少 CPU 精排耗时；C 应扩大到更多经商品可行性核验的多轮案例，并把颜色、预算、两类商品的当前硬约束结构化。上述建议尚未被这 5 条 C 案例证明为普遍收益。

## 7. 最终验证记录

双商品、白色背包聚焦复测分别 ASR/CAR 1.0；最终完整 C 两组各 5/5 ASR、CAR 100%。

删除旧评测脚本后的全量单元测试 `pytest -q`：**32 passed**（另有 2 条依赖弃用警告）；`eval_v3` 的独立脚本导入通过。隔离前端浏览器回归通过：在端口 8012 与专用 SQLite 中，页面发问和商品卡、无商品卡的记忆查询、清空后刷新、删除历史及接口 404 均成功；测试服务已关闭。
